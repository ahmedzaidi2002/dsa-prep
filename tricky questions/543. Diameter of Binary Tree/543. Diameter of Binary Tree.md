# 543. Diameter of Binary Tree — Designing the Recursive Contract

https://leetcode.com/problems/diameter-of-binary-tree/

## The instinct that leads you astray

It feels natural to write `solve(node) -> diameter of subtree rooted at node`,
then combine children like `diameter(node) = max(leftDiameter, rightDiameter, ???)`.
This breaks because **diameter is not a quantity you can rebuild from a
child's diameter alone** — a child's diameter only tells you the best answer
*already found inside* that child's subtree. It throws away the one piece
of information you actually need at the parent: *how far down does this
subtree reach?*

## What does "diameter through node" actually mean?

The diameter of the whole tree is the longest path between any two nodes.
Every such path has a single highest point — the node where it "turns" from
going down-left to down-right (or it's a straight line down one side, which
is just the degenerate case). So:

```
best path passing through node = height(left subtree) + height(right subtree)
```

(counted in edges). This is a fact about **heights**, not about diameters.
To compute it at `node`, you don't need to know the diameter of the left
subtree — you need to know its *height*.

## Why height is the right thing to return

Ask: "what does a parent need from its child to do its own job?" The
parent's job is to compute `leftHeight + rightHeight` for itself, and also
to report its own height upward to *its* parent. Both of those only need
one number per child: **the height of that child's subtree**. So height is
the minimal sufficient piece of information to pass up the call stack —
it's exactly what the recursive contract should return.

Diameter, on the other hand, is not something a parent combines from its
children's diameters. It's the **maximum, over every node in the tree**, of
`leftHeight + rightHeight` computed at that node. That's a single running
answer computed *while* you walk the tree for heights — not a value that
composes cleanly through the return statement.

## The design process, step by step

1. Figure out what "path through this node" costs — here, `leftHeight + rightHeight`.
2. Figure out what a parent needs from a child to compute that at itself — here, just `height`.
3. Make the recursive function return exactly that minimal piece (`height`), since that's the only thing needed to combine at the next level up.
4. Anything that needs to look at *all* nodes' local answers at once (the diameter, which is a max over every node's candidate) is tracked separately — a member variable / reference parameter updated as a side effect during the same traversal, not something you compute by combining return values.

## General pattern

Whenever an answer is defined as "two one-sided quantities meeting at a
node" (diameter = two heights meeting; a similar shape shows up in Binary
Tree Maximum Path Sum, where the answer is `leftGain + rightGain + node
value`), the recursion should:
- **Return** the one-sided quantity a parent needs (height, or max
  downward path sum) — something that composes upward.
- **Track separately** (global/member variable, or pass-by-reference) the
  two-sided combination evaluated at every node, since that's the actual
  answer and it isn't obtained by combining children's *answers*, only by
  combining children's *one-sided values*.

## Standard Code

```cpp
class Solution {
public:
    int diameter = 0;

    int height(TreeNode* root) {
        if (root == nullptr)
            return 0;

        int left = height(root->left);
        int right = height(root->right);

        diameter = max(diameter, left + right);

        return 1 + max(left, right);
    }

    int diameterOfBinaryTree(TreeNode* root) {
        height(root);
        return diameter;
    }
};
```

## Time & Space Complexity

**Time:** O(n) — every node visited once.

**Space:** O(h) — recursion stack, where h is the height of the tree
(O(n) worst case for a skewed tree, O(log n) for a balanced tree).
